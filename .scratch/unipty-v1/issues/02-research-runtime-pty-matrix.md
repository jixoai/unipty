## Question

调查当前 Node、Bun、Deno 及 Linux、macOS、Windows 的 PTY 方案：官方或事实标准实现、原生依赖、权限/安装要求、输入输出与 resize/exit/kill 语义、已知限制和可运行验证方式。特别核实 `node-pty`、`@lydell/node-pty`、Bun 原生 PTY、Deno Node-API 与 `@sigma/pty-ffi`，并区分事实、测量和推断。

## Answer

研究日期：2026-08-18。以下“事实”来自拥有实现或 API 的一手文档/源码；“测量”仅适用于本机 macOS arm64；“推断”不构成 v1 契约。

### 本机测量（macOS arm64，仅作再现基线）

环境：Node `v24.19.0`、Bun `1.3.14`、Deno `2.9.5`。

| Probe                                                                                                                 | 结果                                                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `@lydell/node-pty@1.2.0-beta.15` 运行 `/bin/sh -c 'printf node-ok; exit 6'`，注册 data/exit 并 resize 80x24 -> 100x40 | 安装 2 个包、无源码编译；得到 `{ out: "node-ok", exitCode: 6, signal: 0 }`。                                                                                                                                                                                             |
| Bun `terminal` 运行 `/bin/sh`，write、resize、exit                                                                    | `stdin/stdout/stderr` 全为 `null`；收到 terminal 数据；terminal stream exit 为 `0`，而 `proc.exitCode` 为 `7`。这直接验证两种 exit 语义必须分开。                                                                                                                        |
| Bun 1.3.14 `Terminal.write` / drain 探针                                                                              | 小写入、向读取端写入 4 MiB、向暂不读取的进程写入 16 MiB，均立即返回完整 byte length；分别等待 100 ms、500 ms、1 s 时未观察到 drain callback。该测量证明返回值不提供 readiness，但因前两次可能无需 drain、最后一次尚未恢复 writable，不能据此声称 drain callback 不可用。 |
| `jsr:@sigma/pty-ffi@0.42.0` 运行 `/bin/sh -c 'printf deno-ok; exit 9'`，resize 后轮询 `readBytes()`                   | Deno 下载 `libpty_arm64.dylib`，输出 `deno-ok`，得到 `exitCode: 9`。                                                                                                                                                                                                     |

### 对 UniPty 的推断与风险

1. v1 contract 不能把“数据 chunk 字节完全相同”作为跨平台承诺：Bun 文档明确 ConPTY 会重编码并可合并/重排 VT sequences；`@sigma/pty-ffi` 的 string API 又会经过 UTF-8/C-string 路径。核心应以 byte-capable I/O 为基线，并让 backend 明确其输出表示和保真边界。
2. exit 必须是独立的进程生命周期事件，不能复用 transport EOF：Bun 已证明 terminal EOF 的 0/1 与 process exit code 分离；`node-pty` 和 `pty-ffi` 分别报告进程 exit 状态。
3. `resize` 可作为 core 基础操作，但契约应只承诺“请求尺寸更新或明确 unsupported/error”，不能承诺 Unix `SIGWINCH`、Windows raw mode、像素尺寸或终端序列逐字节效果。
4. `terminate` 不能抽象为可移植 Unix signal：`node-pty` Windows 不支持 signal，`pty-ffi` 只有 best-effort `close` kill。应区分最小的 `close/terminate` 与可选 signal capability。
5. Deno 的候选至少有两条：FFI backend（当前 macOS 通过）与 Node-API adapter（Deno 文档层面受支持，但该 addon 仍需单独通过 contract suite）。二者都不应成为 Deno “原生 PTY”承诺。
6. `drain` 不能被假定为所有候选都能观察的原生 flush：Bun 提供 callback 但 `write` 不暴露是否进入缓冲，`node-pty` 的公开 `write` 返回 `void` 且不提供 drain。公共契约若保留 backpressure，必须由 UniPty/PtyBackend 的 readiness 语义定义，而不是声称等同于底层 PTY 已清空。

### 后续可运行 contract probe

每个候选 backend 在每个宣称的平台至少运行：以结构化 `file + args + cwd + env + initial size` 启动、读取 raw bytes、写入并回显、resize、正常 exit code、主动 terminate、资源关闭后不再发出事件。Windows 另测 ConPTY 的 non-byte-identical 输出和无 signal 行为；Deno Node-API adapter 另测 local `node_modules` + FFI 权限的安装/执行链。
